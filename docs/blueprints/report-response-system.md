## 1. 개요

기존 "처리 중심" (버튼 클릭 → 즉시 처리) 신고 관리를 **"답변 기반 처리"** (검토 → 답변 작성 → 처리)로 개선.

### 변경 전/후 비교

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| **처리 흐름** | 버튼 클릭 → confirm → 처리 | 모달 → 답변 작성 → 처리 |
| **답변** | 선택 (adminNote, 비필수) | **필수** (message, 최소 10자) |
| **사용자 전달** | 불가 | 답변 기반으로 전달 구조 마련 |
| **처리 이력** | reports.admin_note에 저장 | report_responses 별도 테이블 |
| **UI** | 하단 인라인 패널 | 모달 (운영툴 수준) |

## 3. DB 설계

### 3.1 기존 테이블 (reports)

상태 관리만 유지. 구조 변경 없음.

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | bigserial PK | 신고 고유 ID |
| `reporter_id` | bigint FK → users | 신고자 |
| `target_type` | report_target_type | REVIEW / POST / COMMENT |
| `target_id` | bigint | 신고 대상 ID |
| `reason` | report_reason | SPAM / ABUSE / INAPPROPRIATE / FALSE_INFO / OTHER |
| `description` | varchar(500) | 신고 상세 사유 (사용자 입력) |
| `status` | report_status | **PENDING** → RESOLVED 또는 REJECTED |
| `action` | report_action | 관리자 조치 (DELETE_CONTENT / WARN_USER / NONE) |
| `admin_note` | varchar(500) | 관리자 메모 (답변과 동일 값 저장, 하위호환) |
| `processed_at` | timestamp | 처리 완료 일시 |
| `created_at` | timestamp | 신고 접수 일시 |

### 3.2 신규 테이블 (report_responses)

```sql
CREATE TABLE report_responses (
    id              BIGSERIAL       PRIMARY KEY,
    report_id       BIGINT          NOT NULL REFERENCES reports(id) ON DELETE CASCADE,
    admin_id        BIGINT          REFERENCES users(id),
    action_type     VARCHAR(20)     NOT NULL,     -- DISMISS | DELETE
    message         TEXT            NOT NULL,     -- 관리자 답변 (필수)
    created_at      TIMESTAMP       NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_report_responses_report ON report_responses(report_id);
```

**설계 의도:**
- reports 테이블은 상태 관리 책임만 유지
- 답변 이력을 별도 테이블로 분리하여 확장성 확보
- 향후 1건의 신고에 대해 재검토/추가 답변이 가능한 구조

## 4. API 명세

### 4.1 답변 기반 처리 (신규)

```
PATCH /api/admin/reports/{reportId}/process
```

| Body 필드 | 타입 | 필수 | 설명 |
|-----------|------|------|------|
| `actionType` | String | ✅ | `DELETE` 또는 `DISMISS` |
| `message` | String | ✅ | 관리자 답변 (비어있으면 400 에러) |

**처리 로직:**
1. reports 상태 업데이트 (PENDING → RESOLVED/REJECTED)
2. report_responses에 답변 저장
3. reports.admin_note에도 동일 값 저장 (하위호환)

### 4.2 레거시 API (유지)

```
PATCH /api/admin/reports/{reportId}
```

기존 프론트엔드 호환용. `adminNote`가 비어있으면 기본값 "관리자 처리"로 저장.

### 5.2 상태별 동작

| 상태 | 테이블 버튼 | 모달 내용 | 처리 가능 여부 |
|------|------------|----------|--------------|
| `PENDING` | `처리하기` (보라) | 답변 textarea + 템플릿 + 처리 버튼 | ✅ |
| `RESOLVED` | `이력 보기` (회색) | 처리 이력 카드 (readonly, 녹색) | ❌ |
| `REJECTED` | `이력 보기` (회색) | 처리 이력 카드 (readonly, 파랑) | ❌ |

### 5.3 답변 템플릿

| 버튼 | 자동 입력 내용 |
|------|---------------|
| 스팸 | "신고하신 콘텐츠를 확인한 결과, 스팸성 콘텐츠로 판단되어 해당 콘텐츠를 삭제 처리하였습니다..." |
| 욕설 | "욕설·비방이 포함된 것으로 확인되어..." |
| 허위정보 | "사실과 다른 정보가 포함되어 있어..." |
| 정책위반없음 | "현재 커뮤니티 정책에 위반되는 내용이 확인되지 않아 신고를 반려합니다..." |
| 기타 | "신고해주셔서 감사합니다. 검토 결과, " (수동 작성) |

### 5.4 삭제 버튼 동적 문구

| target_type | 버튼 텍스트 |
|-------------|-----------|
| `REVIEW` | 신고 대상 리뷰 삭제 |
| `POST` | 신고 대상 게시글 삭제 |
| `COMMENT` | 신고 대상 댓글 삭제 |

## 6. 원문 조회

### 현재 상태
- 원문 조회 API 미구현
- 프론트에서는 "이미 삭제되었거나 원문을 조회할 수 없는 콘텐츠입니다" 표시

### 후속 구현 시
- `GET /api/admin/reports/{id}/target` API 추가
- 응답: `{ author, createdAt, content }`
- 실제 대상 데이터가 삭제된 경우 → 삭제 상태 플래그 반환

## 8. 후속 범위 (Out of Scope)

> 아래 항목은 현재 구현에 **포함되지 않으며**, 추후 별도 작업으로 진행합니다.

| 항목 | 설명 | 우선순위 |
|------|------|---------|
| **사용자 측 신고 내역 확인** | 사용자가 자신이 접수한 신고의 상태/답변을 조회 | 높음 |
| **신고 처리 알림** | 처리 완료 시 신고자에게 푸시/알림 발송 | 중간 |
| **원문 조회 API** | 신고 대상의 원본 콘텐츠를 관리자 모달에 표시 | 중간 |
| **동일 대상 신고 통계** | 동일 target_type + target_id 기준 신고 횟수 | 낮음 |
| **신고자 이력 조회** | 특정 사용자의 신고 접수/피신고 이력 | 낮음 |
| **답변 수정/재처리** | 처리 완료된 신고에 대한 재검토 기능 | 낮음 |
